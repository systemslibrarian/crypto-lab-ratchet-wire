X3DH — Authenticated Session Setup

Before a single message is sent, Alice derives a shared root key (SK) from Bob's published pre-key bundle. She first verifies the signed pre-key, then combines four Diffie-Hellman secrets. Because every DH term commutes, Bob derives the identical SK from his side — with no interactive round trip. The values below are from this session's live handshake.

Why four DH terms?

  • DH1 mixes Alice's identity with Bob's signed pre-key — it ties the session to her long-term identity.
  • DH2 mixes Alice's ephemeral with Bob's identity — it authenticates Bob.
  • DH3 mixes the two ephemeral-side keys — fresh randomness for forward secrecy.
  • DH4 mixes in Bob's one-time pre-key — so the session stays secret even if Bob's long-term keys later leak.

Out-of-Order Delivery

Networks reorder and drop packets, so messages don't always arrive in the order they were sent. The Double Ratchet copes by deriving the message keys it had to skip and storing them, so a late-arriving message still decrypts. Generate a batch, then deliver them in any order and watch Bob's skipped-key store fill up and drain.

Forward Secrecy — Why Past Messages Stay Safe

The symmetric ratchet's chain key only moves forward: CK[n] → CK[n+1] through a one-way KDF that cannot be reversed. So an attacker who steals Alice's current chain key can read messages from that point onward — but the keys for earlier messages came from chain keys that no longer exist and were deleted the instant they were used. They are unrecoverable. Move the compromise point and watch what the attacker can and cannot reach.

Step 3: Recovery Complete

Bob receives the message and performs a DH ratchet, locking out the attacker

✓ Break-in recovery complete!

Bob's new root key is derived from fresh DH with Alice's new ephemeral key. The attacker cannot compute this without the private keys.

Why This Works

The Double Ratchet's break-in recovery works because:

  • DH Ratchet: Each DH step uses fresh ephemeral keys, making it impossible for an attacker holding old keys to derive new root keys.
  • Asymmetry: An attacker needs the private keys to compute DH, not just public keys.
  • Forward Secrecy: Old message keys are deleted immediately, so past messages remain secure even if the root key is compromised.

The Double Ratchet Algorithm

⚠️ Educational demo — not for production. Ratchet Wire exists to teach how the Double Ratchet works. It runs entirely in your browser with no real contacts, servers, or network traffic. Don't use this code to protect real secrets: it is unaudited, keeps no persistent state, uses a simplified identity model (separate Ed25519 + X25519 keys rather than XEdDSA), and does not address the many side-channels and operational concerns a real messenger must. For genuine end-to-end encryption, use a vetted library such as libsignal(opens in new tab).

Overview

The Double Ratchet (also called the "X3DH + Double Ratchet" protocol) is used by Signal, WhatsApp, and Google Messages to provide:

  • Forward Secrecy: Old messages stay secure even if keys leak
  • Break-in Recovery: New messages become secure after key changes

Two Ratchets

Comparison of Symmetric Ratchet and DH Ratchet
Ratchet Purpose Trigger Output
Symmetric Ratchet Forward Secrecy Every message sent Unique message key
DH Ratchet Break-in Recovery Direction change New root + chain keys

Symmetric Ratchet:

Uses HKDF to derive a unique message key from a chain key:


MK[n] = HKDF(CK[n], salt=0x01, "ratchet-wire-message")
CK[n+1] = HKDF(CK[n], salt=0x02, "ratchet-wire-chain")

DH Ratchet:

Uses fresh X25519 key pairs to derive a new root key and a new chain key (the root key is the HKDF salt, the DH output is the input key material):


root_new ‖ chain_key = HKDF(
    ikm  = DH(my_private, their_public),
    salt = root_old,
    info = "ratchet-wire-root"
)

Key Properties

  • One-way: Chain keys advance forward; you can't derive the previous chain key
  • Deletable: Message keys are ephemeral; no stored history
  • Testable: Both parties use the same HKDF labels, ensuring consistency

Authenticated X3DH

Session setup runs the full X3DH ("Extended Triple Diffie-Hellman") key agreement and authenticates it:

  • Signed pre-key: Bob signs his pre-key with his long-term Ed25519 identity key; Alice verifies that signature before deriving anything. A man-in-the-middle who swaps the pre-key is rejected — try the "Simulate a tampered pre-key" button on the Conversation tab.
  • One-time pre-key: a single-use key contributes a fourth DH, so the session stays secret even if Bob's long-term keys later leak. 

verify  Sig(IK_B, SPK_B)            ← abort on MITM
SK = HKDF( DH1 ‖ DH2 ‖ DH3 ‖ DH4 )  ← DH4 uses the one-time pre-key

Deviation from the spec — the F prefix is omitted. Real X3DH does not hash the DH outputs bare. X3DH §2.2(opens in new tab) defines KDF(KM) = HKDF(F ‖ KM, …), where F is 32 bytes of 0xFF for X25519 (57 bytes for X448). F is there for cryptographic domain separation with XEdDSA. This demo computes HKDF(DH1 ‖ DH2 ‖ DH3 ‖ DH4) with no F prefix, so the shared secret shown above is not the secret a spec-conformant X3DH would derive from the same keys — this demo is not interoperable with real X3DH or libsignal. The line above, and every key the Conversation tab displays, reflects the demo's KDF, not Signal's.

This Demo vs. Production

Faithful to the spec here:

  • Authenticated X3DH (signed pre-key signature + one-time pre-key)
  • Double Ratchet with out-of-order handling and skipped-key bounds
  • Low-order public keys rejected; message headers bound as AEAD associated data

Still simplified (for the demo):

  • The X3DH KDF omits the F prefix (32 bytes of 0xFF) that X3DH §2.2 requires, so derived secrets do not match a conformant implementation — see the note above
  • Identity uses a separate Ed25519 signing key + X25519 DH key, where production Signal uses a single key via XEdDSA (not exposed by Web Crypto)
  • No pre-key server, prekey rotation, or OPK-exhaustion handling
  • In-memory state only (no persistence)
